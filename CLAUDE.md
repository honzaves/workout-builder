# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A full-body workout generator. The app itself is plain HTML, CSS and JavaScript with no dependencies, no bundler and no framework. Python is only used for helper tools. The user-facing docs (field reference for exercises, generator knobs) are in `README.md`. Planned features are in `docs/TODO.md`.

## Commands

```bash
python3 tools/serve.py                  # dev server for web/ at http://localhost:8000/index.html (no-cache, opens browser)
python3 tools/serve.py --no-browser --port 9000
python3 tools/build.py                  # bundle into dist/workout-builder.html (single self-contained file)
python3 tools/serve.py --dist           # serve the built file
python3 tools/validate.py               # check the catalogue in db/workouts.db; run after every data edit (--db other.db)
python3 tools/figures.py review         # dist/figures-review.html: drawings next to their steps (--ids a,b / --pattern squat)
python3 tools/figures.py put f.json     # add/replace poses and drawings; validated, rolled back on errors
uv run --with playwright python tools/redesign_package.py   # UI redesign package: dist/redesign/ + zip (brief docs/redesign/SPEC.md, screenshots of every state; needs Google Chrome)
python3 tools/db_import.py              # one-time seed of a missing DB from the historical exercises.json (refuses on a filled DB without --force)
uv run --with pytest pytest            # all tests (pytest.ini sets testpaths=tests, pythonpath=.)
uv run --with pytest pytest tests/test_data.py::test_build_produces_self_contained_html   # single test
uv run --with pytest pytest tests/test_frontend.py   # JS cases in headless Chrome + a drafts end-to-end run against serve.py (skipped without Chrome; CHROME=/path)
```

Needs SQLite 3.44+ (the one bundled with Python). `.venv/` was created by uv and has no pip, so `pip install` inside it fails; use `uv run --with pytest` for tests. Opening `web/index.html` via `file://` fails because the catalogue is fetched from `/api/catalog`, so always use the server or the built file. There is no linter or formatter configured.

## Architecture

**Data vs. code split.** All data lives in the SQLite database `db/workouts.db` (tracked in git): the exercise catalogue, levels, warm-up/cool-down roles, movement drawings and saved workouts. It is the only source the app uses. `db/seed/exercises.json` is a frozen historical snapshot from before the switch; nothing reads it except `tools/db_import.py` (seeding) and the seeding tests, and it must not be edited. `api.catalog()` flattens the catalogue into one document (`equipment`, `exercises`, `extras`, `quantities`, `levels`, `criteria`, `phases`, `poses`, `figures`) that `web/js/app.js` reads from `window.WORKOUT_DATA`. The level buttons, equipment buttons, rest times and rounds per block all come from it; a new `equipment` row adds a UI button automatically.

**Two loading modes, same app.js.**
- Dev: a `<script>` between `<!-- BUILD:SCRIPTS -->` markers in `index.html` fetches `api/catalog` (no fallback), sets `window.WORKOUT_DATA`, then injects `js/app.js`.
- Build: `tools/build.py` inlines `api.catalog()` from `db/workouts.db` (a snapshot at build time) and regex-replaces the `styles.css` `<link>` and the `BUILD:SCRIPTS` block with inlined CSS, data and JS (escaping `</script`). Keep those markers and the exact `<link rel="stylesheet" href="css/styles.css">` tag intact, or the build fails. The font is bundled in `web/fonts/` (Inter, one variable-weight WOFF2, Latin subset; OFL) and `build.py` embeds it as a base64 data URI, so neither version fetches anything from other sites. Don't add external resources.

**Field-name mapping.** The catalogue uses readable names, and `app.js` remaps them to short keys via `FIELD_MAP` (`name→n`, `pattern→p`, `also_pattern→p2`, `level→l`, `equipment→e`, `reps→r`, `steps→s`, `cue→c`, `avoid→x`, `combo→cb`, `slow_to_fast→ct`, `partner→pt`, `sprint→sp`, `secs→t`, `switch_sides→sw`, `retired→rt`). A new exercise field must be added in five places: a column/table in `db/schema.sql` (plus a migration of `db/workouts.db`), the export in `api.catalog()`, `FIELD_MAP` in `app.js`, `ALLOWED_FIELDS` in `tools/validate.py`, and the README table.

**Generator flow (`app.js`).** Settings `S` → `genQuick(s)` builds a version 2 workout object `{v:2, mode, settings, warm:[{id,role}], cool:[{id,role}], blocks:[{kind:"main"|"course"|"grip", name, rounds, rest?, items:[{id, pat, lv?}]}]}` (see the comment above `upgrade()`; the three modes Quick, Mix levels and Template are described in `docs/design-workout-modes.md` and below). An `id` of `null` is an empty slot; item `lv` and block `rest` fall back to the workout's level via `lvOf()`/`restOf()`. Everything that reads a workout (`sequence`, render, print, `equipList`, Swap, `toDB`) goes through `filled()`/`idsOf()`/`blockIds()` so empty slots are skipped:
- The `blocks` setting (1-6, the length control at the top; stored as `workout.block_count`) is the number of blocks; block i's slots come from `TEMPL[i]` (virtual slots `plyoX` and `squatOrHinge` are resolved randomly in `resolve()`).
- `pick(pattern, s, used, preferCombo, preferPartner, kit)` filters by pattern/`also_pattern`, level, partner and equipment (`ok()`; `"db|kb"` means either), prefers unused ids, then does a weighted random pick. The weights favour the user's level and moves that reuse kit equipment.
- **Equipment kit:** selected equipment is a menu, not a checklist. `genQuick()` keeps a `kit` (`{have:Set, max:KIT[blocks]}`); `pick()` drops candidates that would push the kit past `max` (or, if none fit, keeps those adding the least new gear); unused moves are considered before used ones, so the kit grows by one piece of equipment rather than a move being repeated (except sprints with `prefSp`, where a repeat beats none). `newGear()` lists uncovered requirements; `kitOf()` rebuilds a kit from ids (used by Swap). Course and grip finisher are picked before the blocks so their gear seeds the kit.
- `sprints` setting: `"none"` excludes `sp` moves in `ok()`; `"lots"` turns each block's plyo slot into a sprint slot (or prepends one) and `pick(..., prefSp)` prefers sprint moves there, reusing used ones before giving up.
- The obstacle course is prepended and the grip finisher appended. Warm-up and cool-down draw from `DATA.phases` (`pulse`, `flow`, `mob` for the warm-up; `stretch`, `yin`, `calm` for the cool-down; `exercise_phase_role` in the DB), each filtered through `ok()`; the composition (`pulse[0], flow[0], mob[0], mob[1], pulse[1]`, and `YIN` setting the yin-hold count per block count) stays in `genQuick()`. A new `warm`/`cool` exercise is unused until it has a phase role. `validate.py` checks that each role's ids exist, have the right pattern, and include enough active bodyweight beginner moves (`PHASES` there).
- `sequence(w)` flattens a workout into timed/set/rest steps. It drives the follow-along overlay, the time estimate and the timeline strip. `RESTS` (rest seconds and rounds per block) is built from `DATA.levels`.
- `render()` rebuilds the whole plan as an HTML string. Swap buttons use `data-where="blockIdx-itemIdx"` and re-run `pick()` for that item's `pat`; warm-up and cool-down rows use `data-where="w-i"` / `"c-i"` and pick a random other move from the same phase role(s) in `DATA.phases` (falling back to any role of that phase), skipping moves already in the list and filtered by `ok()`. Next to Swap, **Choose** (`data-choose`, `chooseFor()`) opens the exercise picker (`openPicker(opts)`, a `<dialog id="pickDlg" class="sheet">`: full screen on phones, a bottom sheet on tablets, and from 1024px (`pickWide`) a dialog whose detail (`pickDetail()`) renders into the side pane `#pSide` instead of replacing the list in `#pBody`): `PICK_SECTIONS` sets the categories per section (`main` patterns, `warm`/`cool` roles from `DATA.phases`, `course`, `grip`); `pickPool(state)` is the pure list function (`ok()` with the level check off, then category, tags `sp`/`cb`/`pt`, level ≤ chip, search on names then steps; main matches `p` or `p2`); rows are drawn 40 at a time (`PICK_PAGE`). The detail view's level buttons set the item's `lv` (dropped when it equals the workout level). `changed(sel)` is shared by Swap and Choose: it turns a saved workout into an unsaved copy, stores and re-renders. Headless Chrome screenshots don't show modal dialogs (top layer); for review screenshots patch `HTMLDialogElement.prototype.showModal` to `show()`.

**Mix levels (`S.mode=="mix"`).** `genMix(s)` reuses `genQuick` for warm-up, cool-down, course and grip, then rebuilds each main block from its `TEMPL` patterns plus a 4th (`MIX_EXTRA` rotating per block; `plyoX` instead when `plyo` is "lots" and the block has no plyo). `mixLevels()` assigns levels 4, 3, 2, 1 to the patterns with the most candidates at that exact level (ties random), `pickAt()` picks at the exact level (`pick(..., exact)` with `s.level` 4) or falls back to the nearest level below, then above. Items carry `lv` and are sorted by level; combos/partner/sprint preferences go to one random slot like in Quick. Swap in a Mix workout uses `pickAt()` to keep the level. `validate.py`'s `warnings()` (printed as notes, not errors) lists block patterns without a bodyweight solo move at some level.

**Template mode (`S.mode`, the "How to build it" control).** `syncMode()` hides the `data-not="template"` fields (plyo, sprints, combos) and relabels others (`MODE_LABELS`). `build(mode)` makes `genTemplate(s)`: empty slots (`{id:null,pat,lv:null}` with a hint pattern from `TEMPL`; warm/cool `{id:null,role}`), blocks with explicit `rest` (Intermediate preset) and `rounds` 3. When `W.mode==="template"`, `render()` uses `tplHead()`/`tplSections()` instead of the plan sections; editing buttons carry `data-act` and go through `tplAct()` (auto, fill, up/down/del per slot, additem, rounds, bup/bdown/bdel, addblock with `data-kind`/`data-at`, warmcount/coolcount), the rest `<select>` through `tplRest()`; afterwards `nameBlocks()` re-letters main blocks and `changed()` stores and re-renders. `tplSync()` copies level (= auto-fill level), equipment and partner from the settings panel into `W.settings` before every template action, Swap and Choose; `genSettings(w)` neutralises the hidden sprint/combo settings in templates. Filled template moves always carry an explicit `lv`. `autoFill()`/`fillRest()` use `pick()` with the kit of the filled blocks. `keepsWork()` asks before replacing a template with unsaved work (`W.draftId` + `W.dirty`). Drafts: `saveDraftNow()` (POST/PUT `api/drafts`, document = `draftDoc(W)` without browser-only fields), `openDraft()`, listed first in Saved workouts; saving a full template as a workout (`saveCurrent`) deletes its draft. `toDB()` sends `mode`, item `level` and clamps `settings.blocks` to 1-6.

**Page layout (`index.html`, `styles.css`).** `.app` is a CSS grid of three areas: `#setup` (settings; a sticky sidebar from 1024px, otherwise a card that `fold()` collapses after `build()` below 1024px, with a one-line `#setupSum` and the `#setupToggle` button), `main.main` (`#empty` before anything is built, then `#plan`) and `aside#rail` (`#saved` on top, then `#brief`). From 1280px the rail is a third, independently scrolling column; 1024-1279 it sits above the workout; below 1024 everything is one column (settings, rail, workout). `render()` writes the overview (time card, strip, Start/New/Print, save form, What you'll need) into `#brief` and the evaluations and sections into `#plan`; a template's status card (`tplHead()`) goes at the top of `#plan` inside `.thead` because the `plan` click handler serves its `data-act` buttons. Move rows (`row()`) are a grid inside `summary`: `.nm`, `.rfoot` (`display:contents`) with `.rtags`, `.racts` (Swap/Choose) and the template's `.tctl`; `.list` is a size container, so `@container` rules switch between the narrow two-line layout (icon-only buttons) and one line from 620px. Rule names: the layout uses `.app > .main`, because the follow-along's primary button also has class `main`. The follow-along fills `#fmain` with `.fhead`, `.fclock` (`#fclock`, plus `.fbar > #fbarfill` that `countdown()` drains), `.fcue` and `details.fhow`; `.isjump`, `.isrest`, `.isdone` on `#fmain` and `.paused` on `#follow` drive the styling.

**Persistence.** localStorage keys `fbw-settings` and `fbw-workout` (settings from before the block count had `duration` in minutes; the loader converts 20/30/45/60 to 2/3/4/5 blocks). `loadW()` reads `fbw-workout`, converts a version 1 workout (warm/cool as id lists, `course:true`, grip found by name) with `upgrade()` (also used for workouts from the API via `fromDB`), and discards it if any of its ids no longer exist, so renaming an exercise id silently invalidates saved workouts.

**Validation rules worth knowing (`tools/validate.py`).** Levels are 1–4 (Beginner..Beast); `reps` has 3–4 entries with `""` below the exercise's level. Timed patterns (`warm`, `cool`) skip level/reps. Every core slot (`plyoL squat hinge lunge push pull core`) must keep at least one level-1, bodyweight, non-partner exercise, or workouts can come up empty. `extras`/`quantities` keys must be real exercise ids. Retired exercises don't count toward slot coverage.

**Movement drawings (`FIG` in `app.js`).** A self-contained IIFE between the markers `/* ---------- Figures:` and `/* ---------- end Figures ---------- */`; `tools/figures.py` slices that section into its review pages, so keep it free of other app.js globals (it only reads `DATA.poses` and `DATA.figures`). `FIG.of(id,px)` returns `[{steps:[first,last], top, svg}]` (`px` = expected display width, which sizes the labels); all drawings of an exercise share one viewBox per view (side/top) so the scale stays constant. Poses are JSON: `hip`, `t` (torso, 0 upright, + forward), `hd`, limbs `ln`/`lf`/`an`/`af` (near/far leg/arm) as `{to,bend}` IK, `{a:[upper,lower]}` angles or `{j,to}` explicit joints, `hold`, `hi` (glow), `flip`, `front` (front view: both sides drawn near, far limbs mirror the near ones unless given), `who` (2 = partner colour). World units ~cm, y up, floor y=0, figure faces +x; limb angles 0 down, 90 forward, 180 up. A figure's `x`/`y` shift the whole pose, including any `hip` override, so give an overridden hip relative to the unshifted pose. The comment at the top of the FIG section is the reference for the `hold` values and scene item kinds (figures, equipment such as `box`/`bench`/`rack`/`bosu`/`ball`/`tire`/`ghd`, `arrow` with `dash`/`faint`, `swap`, `guide`, `line`, `label`, and the top-view `pb`/`sq`/`me` when `scene.top`); the validator's `POSE_KEYS`, `LIMB_KEYS`, `HOLDS`, `ITEM_KINDS` must match the engine. Every exercise currently has drawings (usually 2-4, each covering a run of steps); keep it that way when adding exercises: write a `figures.py put` JSON file, load it, and check it with `figures.py review --ids ...`. CSS classes are prefixed `fg-`. `figsHTML(id,px)` renders the captioned strip; `howHTML()` uses it (exercise cards and the follow-along overlay) and so does the print sheet's `move()`.

## Database and API

`db/schema.sql` is the SQLite schema (catalogue + saved workouts, sessions, ratings, evaluations, comments); `docs/database.md` explains the design. Schema changes to the existing DB go in `db/migrations/NNN_*.sql` (apply with `sqlite3 db/workouts.db < file`) as well as `db/schema.sql`. `tools/api.py` is the single DB entry point: `connect(path, create=False)` refuses a missing file (only `db_import` passes `create=True`), `catalog()` builds the app's catalogue, and the workout functions handle saving and evaluating. `tools/serve.py` never writes the catalogue; it refuses to start on a missing DB or one with no active exercises. `tools/db_import.py` seeds from the JSON snapshot (upsert by slug; exercises not in the JSON get `is_active = 0`, so running it with `--force` on an edited DB retires DB-only exercises); its `PHASES` constant holds the warm-up/cool-down lists that used to be hardcoded in `app.js`. Retired exercises (`is_active = 0`) come back to the app as `retired: true`, which `ok()` skips; never delete an exercise, since `workout_item` references it. Saving and evaluating go through `tools/api.py`; the app switches those features on only if `GET /api/workouts` answers (`API.on`), so the built single file still works without a server. `toDB()` in `app.js` converts the on-screen workout into the shape `api.save_workout` expects (which refuses empty slots); `get_workout` returns the version 2 shape (`v`, `mode`, warm/cool as `{id, role}` with the role looked up via `exercise_phase_role`, blocks with `kind`, `rest` for main/grip, items with `lv` when stored). Drafts (`workout_draft`, migration `003_workout_modes.sql`): `list_drafts` (with `slots`/`empty` counts), `save_draft`, `get_draft`, `update_draft`, `delete_draft`; routes `GET/POST /api/drafts`, `GET/PUT/DELETE /api/drafts/<id>` (`do_PUT` in `serve.py`). Catalogue mapping: `pattern`/`also_pattern` → `exercise_pattern`, `"a|b"` equipment → `exercise_requirement` + `requirement_option`, `extras` → `setup_item`, `quantities` → `exercise_coaching.setup_note`, `phases` → `exercise_phase_role`, `poses` → `figure_pose`, `figures` → `exercise_figure`. Tests never touch `db/workouts.db` except read-only (`test_data.py` validates it and checks the build); `test_db.py` seeds temporary DBs from the JSON. `test_frontend.py` appends `tests/frontend/cases.js` to a copy of the built file, runs it in headless Chrome (`--dump-dom`, no `--user-data-dir`: Chrome hangs on exit with one) and reads the JSON it writes into `<pre id="fbw-results">`; the cases reach app internals through `window.FBW` (end of `app.js`, unused by the app). It also saves the cases' `toDB()` output (a quick workout and a template) through `api.save_workout` on a copy of the DB, and `tests/frontend/drafts_e2e.js` runs the draft flow against `serve.make_server` with a temporary DB copy. Inline test or screenshot scripts must be wrapped in a function: `app.js` has top-level `const`s (e.g. `F`) that a second `const` would clash with. Headless screenshots don't scroll reliably after focus changes; stub `focus`/`scrollIntoView` for review shots. SQLite needs `PRAGMA foreign_keys = ON` per connection.

## Conventions

- `app.js` is written in a dense, minified-like style (short names, one-liners, template-string HTML). Match it rather than reformatting.
- Theming uses CSS custom properties on `:root` with a dark override under `prefers-color-scheme` (repeated for `:root[data-theme="dark"]`); use the existing tokens (`--strength`, `--jump`, `--soft`, `--partner`, spacing `--s1..8`, radii `--r*`, `--tap`, etc.) rather than raw values. The token table, type scale, layout per breakpoint and component specs are in `docs/redesign/DESIGN.md`.
- Icons are `<symbol>`s in the sprite at the top of `index.html` (`#i-swap`, `#i-choose`, `#i-chev`, ...); `ic(name)` in `app.js` returns `<svg class="ic"><use href="#i-name"/></svg>`. Buttons whose label JS changes temporarily (Swap's "No other options", Auto's "Nothing fits") keep the text in an inner `<span>` and add class `says` so narrow lists show it.
- `dist/` is build output and git-ignored.
- The README says Python 3.9+ (the tools need `Path.is_relative_to`), but `pyproject.toml` declares `requires-python >=3.14`; the tools themselves use only the standard library.
